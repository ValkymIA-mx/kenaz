# M0 CONTENT draft — 2026-11-09

## Result and boundaries

`content/site-list.schema.json` defines the draft JSON Schema 2020-12 format; `content/sites.en.json` and `content/sites.es.json` contain the same ten providers, four email providers first. `content/glossary.md` gives bilingual plain and advanced terms. The list is a research draft, not a frozen M1 contract or release-ready guide. Entries cite primary provider help checked on the date recorded in each source. No account was enrolled and no live registration, translation, accessibility, usability or physical-key test was performed. Provider instructions, account types, regions, browser support and product availability may change; review them again before release.

Each method and the backup-code field use `supported`, `unsupported`, or `unknown`: unknown is not a negative or permission to claim support. `physical_key_passkey` specifically means a passwordless passkey on a roaming physical authenticator; a platform/synced passkey alone does not establish it. `security_key_after_password` is the separate second-step path; `totp_codes` means authenticator-app codes, not SMS. `backup_codes` includes a provider account recovery code and does not imply identical recovery behaviour. Settings are entry points; some may require sign-in or navigation. Supported methods may have prerequisites (notably Dropbox and GitHub), or vary by account; consult each citation. The steps document one evidenced path, not a guarantee that every supported method can use the same steps. A YubiKey Security Key does not support TOTP; code setup needs compatible keys.

Google documents physical FIDO2 passkeys and may delay new keys up to seven days. Proton requires the platform-key option to remain unchecked for a physical key. Dropbox requires an existing code method before a security key and limits where it works. Discord distinguishes passwordless passkeys from security keys typically used after a password; its physical-key passwordless capability remains unknown. Microsoft recovery is an account recovery code, not necessarily a 2FA bypass; retain its other recovery methods. Facebook may display either Accounts Center or Meta Account settings. Bitwarden calls its security-key second factor “Passkey”; this alone does not establish a passwordless physical-key passkey.

## Validation

Validate each localized document against `content/site-list.schema.json` using any JSON Schema Draft 2020-12 validator with format checking enabled, then compare IDs/order and ensure the first four categories are email. For example, if Python's `jsonschema` package is already available (no install required):

```sh
python -c 'import json, jsonschema; from pathlib import Path; p=Path("content"); s=json.loads((p/"site-list.schema.json").read_text()); v=jsonschema.Draft202012Validator(s, format_checker=jsonschema.FormatChecker()); a=[json.loads((p/("sites."+l+".json")).read_text()) for l in ("en","es")]; [v.validate(x) for x in a]; ids=[[y["id"] for y in x["sites"]] for x in a]; assert ids[0]==ids[1] and len(set(ids[0]))==10; assert all(y["category"]=="email" for x in a for y in x["sites"][:4]); print("schema and bilingual ordering OK")'
```

Validation was run successfully during integration with Python's installed `jsonschema`: the schema itself is valid Draft 2020-12, all 20 entries validate with format checking, both languages have the same ten unique provider IDs in the same order, and the first four entries are email providers. Schema validation does not establish that provider claims or translations are correct.
