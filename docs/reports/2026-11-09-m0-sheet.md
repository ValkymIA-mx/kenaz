# M0 SHEET: recovery sheet spike

**D5 is decided: embed Typst.** Both paths were built and rendered offline on the Linux x86-64 host with only bundled fonts. The [decision](../decisions/2026-11-09-recovery-sheet-renderer.md) records why; this report records the experiment, not production secret handling.

## Experiment

From the repository root, after Cargo dependencies have been fetched and the lockfile generated:

```sh
cargo run --offline --manifest-path spikes/sheet/Cargo.toml --release --features embedded
```

The Rust program uses `qrcode` to encode an `otpauth://totp/` URI from the first example account and replaces that account's existing `qr_svg` in a generated copy of the JSON. The template reads that SVG as an image. The second account stays unchanged to retain the reference layout. Sample-only PDF, SVG and JSON go under `spikes/sheet/target/sheet-sample/`. This code writes plaintext sample secrets; never use real secrets in this spike. Rust prints duration and PDF size for each path. CLI time includes process startup; embedded time includes loading fonts and constructing the world. Neither includes Cargo build time.

The program calls the installed `typst` CLI with an explicit repository root, only the bundled font directory, and both system and Typst-embedded fonts disabled. The template has no package imports; render needs no network. `typst` and Poppler's `pdfinfo` and `pdftotext` are prerequisites. The observed CLI is Typst 0.15.1; versions can affect output. Cargo needs a one-time dependency fetch before offline execution.

The bundled fonts came from Arch's `noto-fonts 1:2026.11.01-1` (Noto Sans regular and bold) and `ttf-dejavu 2.37+18+g9b5d1b2f-8` (DejaVu Sans Mono regular and bold), with their respective distribution licence files alongside them. `pdffonts` on the English reference identifies those four families/styles. Font provenance and licence files do not by themselves prove the rendered output uses them or covers every future input character.

`pdffonts` on the embedded English output confirms all four expected fonts are embedded: Noto Sans regular/bold and DejaVu Sans Mono regular/bold. Both renderers warn that unused fallback families (DejaVu Sans, Noto Sans Mono and Liberation Mono) are absent. They still use the bundled selected families; warnings are retained rather than suppressed.

## Reference checks

Run `python3 spikes/sheet/compare.py` to check both paths against the reference page counts, dimensions, and selected text markers. It does not check the entire document or scan the QR. For detailed text differences:

```sh
for lang in es en; do
  pdfinfo "templates/recovery-sheet/example-$lang.pdf"
  pdfinfo "spikes/sheet/target/sheet-sample/example-$lang.pdf"
  pdftotext "templates/recovery-sheet/example-$lang.pdf" "spikes/sheet/target/sheet-sample/reference-$lang.txt"
  pdftotext "spikes/sheet/target/sheet-sample/example-$lang.pdf" "spikes/sheet/target/sheet-sample/rendered-$lang.txt"
  diff -u "spikes/sheet/target/sheet-sample/reference-$lang.txt" "spikes/sheet/target/sheet-sample/rendered-$lang.txt" || :
done
```

Inspect differences rather than treating byte equality as the criterion: references predate the change from `yubicox` to `Kenaz` and contain the older secrets path. Check matching page size/count and that titles, account details, warning, and recovery instructions survive in both languages; inspect layout and decode the printed QR independently before accepting it. The reference PDF and the current JSON/template are not identical, so this is not an exact golden-text test.

Observed: all four PDFs (CLI/embedded × es/en) match the reference's three US Letter pages (612 × 792 points) and selected content markers. Page 2 of every generated PDF was rasterized at 200 dpi with `pdftoppm` and decoded by `zbarimg --quiet --raw`; the generated QR's scheme, type, decoded label, secret, issuer, algorithm, digits and period all matched the example account. The embedded Spanish second page was also visually inspected; this is not a full print-layout audit or a physical paper scan.

One host run measured CLI es/en at 21/18 ms and embedded es/en at 15/12 ms. These are observations, not a performance claim: CLI includes process startup, versions differ, and this is not a repeated controlled benchmark. Generated PDFs were 97,907/97,214 bytes (CLI es/en) and 97,725/97,032 bytes (embedded es/en).

## Embedding versus CLI

The CLI is a separate executable and process, with an explicit filesystem root and font search policy; it requires deployment and versioning of that executable. The embedded path uses `typst` and `typst-pdf` 0.15.0, with a `World` that serves only the template and generated JSON and loads only the four bundled fonts. Both consume the same generated JSON. Embedding avoids an external executable but moves integration and resource management into the application. See the [compiler API](https://docs.rs/typst/0.15.0/typst/) and [World API](https://docs.rs/typst/0.15.0/typst/trait.World.html). CLI 0.15.1 and embedded 0.15.0 differ, so these numbers do not rank their performance. D5 selects embedding for deployment and in-memory data handling, not these timings.
