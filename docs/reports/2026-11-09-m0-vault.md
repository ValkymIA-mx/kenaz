# M0 VAULT: source investigation and experiments

Status: **D1–D4 pending**, not an ADR. All three software experiments below were built and run successfully on the Linux x86-64 host. No hardware, plugin interoperability, SSH, GnuPG or Thunderbird acceptance is claimed. No Yubico USB device or age plugin was available. The experiments do not write private keys to disk or print them; core dumps, swap and full memory-zeroization are outside their guarantees. Cargo downloads/build output do not contain generated private keys.

## Run

From the repository root (the dependency lockfile is included):

```sh
cargo run --locked --manifest-path spikes/vault/Cargo.toml --bin age_boundary
cargo run --locked --manifest-path spikes/vault/Cargo.toml --bin openpgp
cargo run --locked --manifest-path spikes/vault/Cargo.toml --bin certificates
```

Each binary aborts on failed assertions. `age_boundary` exercises custom public recipient/identity implementations, a wrong identity, and tampered ciphertext. Its deliberately renamed X25519 stanza is **not** a hardware-plugin format. `openpgp` generates secret keys in memory for both candidates and checks Sequoia policy-bound keys and rPGP's cryptographic bindings and detached signature including altered data. `certificates` parses each P-256 certificate and verifies its self-signature, including altered TBS rejection. These are software experiments, not production secret handling.

Observed results: custom age stanza encryption/decryption, wrong-key and ciphertext-tamper rejection passed; Sequoia policy validation and rPGP binding/signature verification passed; rcgen and x509-cert P-256 self-signature verification and altered-TBS rejection passed. The x509-cert builder uses the DER ECDSA signature type required for X.509 BIT STRING encoding. These results establish software API feasibility only.

## D1: age boundary and actual plugin formats

[age's public Recipient](https://docs.rs/age/0.11.2/age/trait.Recipient.html) returns stanzas and labels; [Identity](https://docs.rs/age/0.11.2/age/trait.Identity.html) returns an optional file-key result per stanza and permits overriding whole-file stanza handling. This is an API boundary through which a card-backed operation can be implemented, not proof that `yubikit` supplies the required operations or that either plugin accepts the resulting files. The existing [plugin protocol](https://docs.rs/age/0.11.2/age/plugin/index.html) remains a possible fallback.

The YubiKey plugin's [legacy PIV implementation](https://github.com/str4d/age-plugin-yubikey/blob/main/src/piv_p256.rs) uses `piv-p256`, a four-byte key tag and compressed ephemeral P-256 point as unpadded base64 arguments; ECDH, HKDF with the `piv-p256` label and a salt of the compressed ephemeral and recipient public points produce the wrapping key. It decompresses the ephemeral point for the hardware operation. The [recipient dispatcher](https://github.com/str4d/age-plugin-yubikey/blob/main/src/recipient.rs) also handles the newer `p256tag` path. A compatible implementation must select and match the actual plugin variant and identity metadata, not just implement generic ECDH.

The FIDO plugin's [recipient source](https://github.com/olastor/age-plugin-fido2-hmac/blob/c4904216d6895c7992e01211239c588583e8e6b4/pkg/plugin/recipient.go) handles version 1 differently; version 2 wraps with native X25519 and stores version, ephemeral share, PIN flag, salt and credential ID in `fido2-hmac` stanza arguments, and version 3 uses a hybrid recipient. Its [identity implementation](https://github.com/olastor/age-plugin-fido2-hmac/blob/c4904216d6895c7992e01211239c588583e8e6b4/pkg/plugin/identity.go) obtains the hmac-secret from the token, handles native as well as plugin stanzas, and uses the output as an X25519 identity. The [v2 specification](https://github.com/olastor/age-plugin-fido2-hmac/blob/c4904216d6895c7992e01211239c588583e8e6b4/docs/spec-v2.md) is draft. Versioning and metadata are material interoperability requirements.

Still required: real YubiKey 5 and Security Key, relevant plugin binaries, and implementations of their real recipient/identity formats and card operations. For each applicable PIV and FIDO option encrypt in-app and decrypt using its plugin, then encrypt with that plugin and decrypt in-app; verify the plaintext and negative cases. Do not infer this from the generic test.

## D2: unlock choice remains open

| Option | Documented scope | Interoperability gap |
|---|---|---|
| OpenPGP | YubiKey 5 with supported Curve25519 firmware; not FIDO-only Security Key | Card X25519 and `age-plugin-openpgp-card` not exercised |
| PIV | YubiKey 5, not FIDO-only Security Key | PIV stanza variants and `age-plugin-yubikey` both directions not exercised |
| FIDO2 | FIDO2 hmac-secret capable YubiKey 5 and Security Key | `age-plugin-fido2-hmac` both directions and actual PIN/touch behavior not exercised |

These are documented capabilities, not observations on this hardware matrix; see [product scope and linked vendor sources](../../IDEA.md#what-opens-the-file-the-user-chooses). Install/packaging availability on supported guests, paired-key and replacement behavior remain to be measured. Windows elevation/CCID is an M5 unknown. Do not choose the M2 recommendation before those gates.

## D3: OpenPGP candidates

[Sequoia CertBuilder](https://docs.rs/sequoia-openpgp/2.4.2/sequoia_openpgp/cert/struct.CertBuilder.html) offers Cv25519 and subkey flags; its [Cert](https://docs.rs/sequoia-openpgp/2.4.2/sequoia_openpgp/cert/struct.Cert.html) canonicalizes and mathematically checks self-signatures, and `with_policy` applies policy. This experiment selects its pure-Rust experimental backend; this is not a backend or security decision. [rPGP's builder](https://docs.rs/pgp/0.21.0/pgp/composed/struct.SecretKeyParamsBuilder.html) exposes v4, Ed25519 legacy and ECDH Curve25519 legacy, plus binding verification and signature APIs. Its [README](https://github.com/rpgp/rpgp#rpgp-is-a-low-level-openpgp-library) says applications must handle higher-level OpenPGP semantics. Both can generate secret material in memory, but code here does not extract and import it via `yubikit`: card readiness, layouts, import, actual GnuPG/Thunderbird acceptance and safe secret lifecycle remain unproven. Use two test YubiKey 5s and suitable GnuPG/Thunderbird installations; preserve private material exclusively in memory or encrypted storage.

## D4: P-256 candidates

[rcgen](https://docs.rs/rcgen/0.13.2/rcgen/struct.CertificateParams.html) self-signs from certificate parameters and a key pair; [x509-cert](https://docs.rs/x509-cert/0.2.5/x509_cert/builder/struct.CertificateBuilder.html) builds from an explicit profile, subject, public key and signer. Both provide an in-memory generation route, but a self-signature does not demonstrate SSH acceptance, correct product certificate profile or PIV slot import. The spike does not write to slot 9a. Complete both candidates with test YubiKey 5 hardware, `yubikit`, and an SSH smart-card stack configured for the relevant certificate; verify a challenge signature and actual SSH authentication before D4.
